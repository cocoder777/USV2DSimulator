# 当前 Jev 控制与协议

Unity 采样并暂停 → Python 整理航路点和 64 个 Choice → Jev 选择全局目标航速/航向 → Unity 平滑执行固定时长 → 再次采样。地图虚线只显示和保存在轨迹中，不进入 UDP 观测、模型状态、提示词或候选评价；点间路径由 Jev 自主决定。

## 观测与坐标

Unity 世界 +X 为东、+Y 为北，1 单位为 1 米。模拟经纬度基点为 120.5°E、30.2°N。`boat` 按甲方态势字段提供解码后的物理量：

| 字段 | 含义 |
| --- | --- |
| `longitude`、`latitude` | 船的当前经纬度，单位度 |
| `targetSpeed` | 当前实际有符号航速，单位节；1 节 = 1852/3600 m/s |
| `targetCourse` | 当前速度向量的全局方向，北为 0°、顺时针；倒车时与船头相反；静止时为 `null` |

这些 `target*` 字段是观测，不是控制目标。不发送船头、转速、当前指令和剩余过渡时间。`null` 是本机 JSON 对不可观测方向的约定，不是甲方二进制字段取值。二进制缩放、量化与特殊值解码待正式接入时实现。

`task.planWaypointList` 为 `routeLon/routeLat/routeSpeed` 对象列表；`routeSpeed_unit=m/s` 明确本仿真单位，甲方文档尚未明确该业务字段的单位，不把态势航速的“节”直接套到它上面。任务还提供点数、当前目标序号、到达半径和终点停车阈值。没有虚线采样或虚线前视。

`planning` 提供动作时长、暂停决策标志。`execution` 仅提供已知仿真配置：速度与航向响应时长，默认各 0.5 秒；它们不是额外船况观测。`action_space` 提供 8 档 `speeds_knots` 和 8 个 `courses_deg`。

Python 使用采样船位为原点、始终朝东/北的局部米制坐标，向模型描述“东/西多少米、南/北多少米”。不使用船头视角，不从静止时的未知运动方向推造艏向。

## 计划航速与判定

每点 `routeSpeed` 只表示通过该点到达圈期间的实际航速绝对值上限，不是参考速度、不要求达到。点间不施加该点上限；通过后仍在圈内时继续遵守该圈上限。起点只表示初始位置，不对离开起点的航速作限制。

普通地图中间点交替配置 2.5、1.75、3.75 m/s；Level4 使用 1.0、1.75、2.5 m/s。终点通过上限为 1.0 m/s，圈内完成停车阈值独立为 0.1 m/s。数值保存在地图文件中，模型读取本次观测，不写死在提示词中。

Unity 沿物理步的扫掠线段计算入/出圈区间，并对步首/步末实际速度插值得到圈内最高航速；不是仅取决策末速度。普通点记录首次有效通过至首次出圈的最大值，终点记录有效目标期间所有入圈过程至完成的最大值。结果保存在 `passing_max_speeds_mps`，地图同时显示配置上限及实测最高值。

超限只记录和显示，不强制裁剪模型指令，也不阻止打卡。中间点按序入圈即可；终点必须当前位置在圈内且实际航速绝对值不超过停车阈值。完成不要求角速度归零。任务仍由 Unity 唯一判定。

## Jev 请求与简化预测

HTTP 正文为 `model/state/questions`，`state` 包含 `task/boat/target/upcoming_waypoints/execution`，必要时补充尚未离开的已通过点圆圈上限。完整样本见 [choice64_request.json](../../jev_api/examples/choice64_request.json)。

候选描述目标全局航向和非负速率，以及近似轨迹、中点、终点、入圈、圈内最高速度、是否超限和继续保持同指令两段时长的预览。实际只执行一段，不预先安排下一动作。没有贴线偏好、候选打分、排序、过滤或代选。

目标刚切换但船尚未离开上一点圆圈时，候选另列上一圆圈内的预测最高速度和超限标志，避免提前加速。当前目标另提供到达半径 25% 的外扩预测提示区，提醒在不确定的转向预测下提前减速；该提示不改变实际到达圈、速度上限或任务判定。点间进展以到当前目标距离的减少量描述，不再使用沿虚线进度。

预测只依赖当前运动速率和运动方向，假设零初始转速及完整响应时长；静止时用候选方向作估计起始方向。缺少艏向、转速和执行器进度，因此启动、急转和连续同指令的预测可能与 Unity 不同。请求明确标注这些估计不构成实际轨迹或限速保证，不能把运动方向冒充测得的船头来宣称精确预测。

## 输出与执行

8 档速率占最大前进速度的比例为 `[0,0.05,0.1,0.2,0.35,0.5,0.75,1]`；8 个全局航向为 `[0,45,90,135,180,225,270,315]`，北起顺时针。Jev 选择一个 Choice，Python 解码为物理量：

```json
{
  "type": "decision_result",
  "session_id": "s",
  "episode_id": "e",
  "run_id": "r",
  "decision_id": "d",
  "tick": 0,
  "action": {"speed": 4.859611, "course": 90},
  "action_duration_s": 0.4
}
```

`speed` 为非负目标速率（节），示例约 2.5 m/s；`course` 为全局目标运动方向（度），示例向东。不是船体相对转角，也不是速度增量。当前不提供倒车动作；相反方向用另一全局航向表达，手动模式仍可倒车。

Unity 执行器将 `course` 转成内部东起逆时针角度 `90-course`，以船内部实际艏向/转速完成平滑转向，并将节转换为 m/s。零速度指令保持接收时的艏向进行减速，不因 Choice 的方向值旋转到北方。速度采用固定响应时长匀加速，航向采用三次 Hermite 过渡；相同目标继续原过渡。物理模型仍可能存在残余旋转，模型只掌握简化运动预测。

此输出约定是本项目当前的明确选择。甲方 `Speed/Course` 表未明确控制坐标系与单位，不能据此宣称已兼容真实动力系统；正式接入需要独立确认并实现输出适配。

## 通信边界

本机 Unity `127.0.0.1:5005` ↔ Python `127.0.0.1:5006`，使用 UDP，每数据报完整 UTF-8 JSON，上限 65000 字节，无应用层分包。保留身份、tick、速度范围、航向范围和动作时长校验，拒绝重复、过期或非法结果。等待时仿真暂停，请求/结果各发送一次；失败通过 Retry Jev 重新采样，不自动重发。

决策请求、决策结果、错误回复和完成通知均不携带自定义版本号；消息类型和其他字段保持不变。接口按具体结构与运行身份校验，不再维护通信版本常量。地图及轨迹文件的 `schema_version` 不受影响。

甲方二进制组播、`status=1/2/3` 和转弯半径仍未接入。[对接说明 V1.0](../甲方接口/对接单艇决策服务.md) 的“每包带 `contentLength`”与新增 Excel 的“仅首包带长度”、帧编号存在冲突，正式对接前统一；本次不实现该通道。

### 2026-10-21：代码结构清理

预测统一为 `predict_ground_motion`，删除旧版预测入口、任意初始转速参数和未使用的结束艏向/转速返回值，共用轨迹与逐点速度的时间分段。保留原来的积分、舍入及旋转顺序，避免影响临界入圈分类和候选文字。

原 `route_context.py / RouteContext` 改为 `tools/waypoint_geometry.py / WaypointGeometry`，按观测创建，移除无用的 `run_key` 和线程内长期保存的几何对象。候选计算及自然语言描述拆成私有函数，单次循环生成最终候选。Unity 只移除四个不再使用的公开执行状态属性，内部动力学保持原样；测试改用现有全局预测入口。

清理前后比较：288 份最终真实观测加五张地图的初始观测，共 293 份完整 payload 序列化后逐字一致；覆盖静止、倒车、近零速度、跨北向和非整物理步响应的 2592 组预测，其保留输出完全一致。17 项离线测试通过，Unity 编译零错误/警告。本轮未新增真实 API 调用，未修改 Logs、SDK 示例、requirements 或完整请求样本。
