## 条件与判定口径

复用 `Tools/control_benchmark.py`、现有九场景以及独立的 `D:\AI\Laya\validation-project`。测试是实际 Unity Editor 的 batchmode / nographics 物理闭环，不是 Python 运动模拟替代 Unity。原项目 Assets、场景和动力学保持不变；副本仅使用隔离 UDP 端口 15005 / 15006。复测期间用户先要求默认切换 Kev，随后改回 Laya，均已完成；各轮测试通过显式 `--backend laya|kev` 指定模型，运行中的测试不受默认值变更影响。

四组使用同一场景 JSON、初始状态、当前目标、动力学和 56 动作表。逐场核对初始 tick=0、位置、航向、速度、角速度，并核对初始完整 observation 与 PD 基准一致。PD / Lookahead 复用已经成功的原始日志；本轮新跑 Laya / Kev。Classic 不重复调参。

等待模型决策时仿真暂停，推理耗时会增加墙钟等待，但不会把正向加速度变成负向，也不会在等待期间额外积分运动。本轮导航问题不能仅用“推理慢”解释，需结合原始动作与闭环状态判断。

## WinError 10061 证据与结论

旧运行 `Logs/control-benchmark-20261018-laya/` 的结果不能作为九次模型决策失败：其中一次墙钟超时，八次服务不可连接。前两场有部分有效运动，其他场没有有效执行，但都未完成原定导航评估。旧记录独立保留，不混入新轮成功率分母。

| 证据 | 观察 |
|---|---|
| 旧服务记录 | 父进程 32840，Uvicorn 子进程 11420；诊断时二者均不存在，8010 无监听 |
| 旧服务文件 | service-20261018-192558.out.log 最后写入约 20:01:58；stderr 只包含正常启动及 Windows distributed redirects 提示 |
| Python/CUDA 错误 | 没有留下 Python traceback、CUDA out of memory 或正常关服退出信息 |
| Windows 事件 | 查询当日 19:00 后 Application 1000/1001 及 System 2004/4101；仅发现 EdgeUpdate 错误，无匹配的 Python 崩溃、资源耗尽或显示恢复事件 |
| 历史缺项 | 没有服务退出码、退出瞬间显存或完整系统资源曲线，不能追溯证明是谁或什么结束了进程 |

可确认的直接原因是服务进程已退出、端口不再监听，客户端连接被拒绝。进程为什么退出仍然证据不足；现有证据不支持直接认定显存不足，也不能凭“没有日志”彻底排除未记录的资源或进程终止问题。旧服务清单已先复制留证，再用原脚本重新启动；没有重装部署或修改权重。

新测试每约 5 秒记录整卡已用显存、GPU 利用率、端口状态和客户端存活，并持有服务父/子进程句柄监控真实退出码，259 表示仍在运行。采样最大值不等于瞬时显存峰值，也不能替代旧运行缺失的历史数据。本轮测试结束后的人工停服与测试中断分开处理。

## 指标定义与统计修正

- 导航成功率 = 成功 /（成功 + 完整仿真预算内未达标）。服务中断、HTTP/墙钟超时、非法响应及未运行单列，不直接计为导航失败。
- 原因 `timeout` 表示 **仿真时限耗尽**，与 `wall_timeout` 或 HTTP 请求超时不同。前者仅在实际完成仿真预算后记为导航失败。
- 最终目标距离：由最终世界位置重新计算。前六场以指定打卡点为目标，其余以终点 E 为目标；多点任务另保留当前待过点距离。不能把 Mission.Next 为空时的占位零当作实际距离。
- 路径偏差：每个实际固定步的位置到整条参考折线/采样曲线的最近欧氏距离，按步骤计算最大值、平均值和 RMS。它不是有符号横向偏差，也不验证沿路径方向和通过顺序；通过顺序由原任务逻辑判定。
- 停车速度：需要停车的场景使用末态 abs(speed)；打卡场景不评价停车，仍保留有符号末速。
- 决策耗时：唯一请求在 Python 决策函数内的耗时，模型含 HTTP/推理/解析，Classic 为控制器计算；不含 Unity 的动作执行时间。保留首次请求，提供 mean/median/p95/max，不把低耗时当作导航能力。
- 未执行场景的末态/偏差记为 null，避免“零误差”的错误印象。重新汇总仅写入新目录，不覆盖旧 summary 或原始日志。

## 原始回答与执行链核验

`compare_control_runs.py` 通过 decision_id 关联 request、原始 raw_response、解析动作和轨迹；核对模型原始候选与发往 Unity 的动作一致。复用现有 `classic_control.predict_action`，从决策前观测预测完整 0.4 秒动作，再与真实 Unity 的第 20 步状态比较；最后提前结束的动作不强行凑满。数值误差按各字段自身单位检查，不把角度误差写成位置误差。详细数量及误差见统一 JSON。

这项检查验证传输/映射/执行与当前动力学一致，不能把合法执行理解成模型选择合理。预测器默认采用本轮已核对的 0.02 秒和零时间常数，不能直接用于其他动力学配置的结论。
